# local.44：通用交付和执行所有权

## 证据与边界

玩家在 local.42 上报告多个目标（含 EMC 与非 EMC）显示 100% 后不出料/不释放 CPU。日志还显示认证游标停在最后一个制作步骤，不能仅凭界面百分比认定物品已到齐，也不能直接认定是“实际出料大于预期”。

代码核查发现，除 NeoECO 之外，Thunderbolt 的原生与 AdvancedAE CPU 适配也会在正常 `executeCrafting` 外先调用 `BatchExecutor.runBatchOnly`。该路径直接修改原生任务计数，不经过认证提取/接收钩子。之前只隔离 NeoECO，没有覆盖这条共享批处理入口。这是独立于物品种类的执行协议问题；并非给某张精华或 EMC 样板设例外。

另外，原交付门槛要求目标键的估计回料数清零。机器少返回了某些估计余量时，即使实际目标已经足够，仍可能不结束。多产通常应表现为余量，不应成为等待更多目标的依据。本轮同时处理这两个通用条件，不把所有症状混成同一个已经实机确认的根因。

## 执行所有权

`CertifiedExecutionScope` 只覆盖同步 CPU tick，不持有网格或模式黑名单。进入认证 CPU 时受限，嵌套普通 CPU tick 暂时恢复普通能力，退出或异常时恢复原状态，其他线程不受影响。

`ThunderboltBatchCompat` 在 common setup 使用实际安装版本的公开批处理资格注册接口。认证作用域内返回“不使用批量旁路”，调用方回退普通逐次派发；不跳过整个任务、不清空任务表、不修改预测产物。普通任务不被全局禁用。原有 NeoECO 认证所有权守卫保留。

## 交付规则

```text
程序尚有未派发步骤：可交付量 = 0
程序已派发完成：
  可交付量 = min(剩余目标, max(0, 实际目标库存 - 初始目标资本))
收到接收方的实际接受量后：
  只扣这部分真实库存，减少同样数量的剩余目标
  剩余目标为 0 -> 原生完成/回库，CPU 释放
```

估计 `waitingFor` 仍用于正常回料接收，但不是目标交付必须清零的条件。未返回的副产物或多估的目标余量不再独立锁住已满足的目标。额外实物、容器和初始资本留给原生清理/回库；迟到和超出接收配额的产物按正常网络存储路径处理。

初始目标资本必须保留：若使用 1 个目标作为种子，本次要求净新增 3 个，而实际 CPU 里只有 3 个，最多交付 2 个，不能花掉种子冒充完成。旧保存程序从全部程序的前缀需求恢复这部分资本，不根据当前库存猜测进度，也不修改 NBT 格式。

真实不足、满库存、接收方阻塞和原生任务/认证游标脱节仍不得强行标完成。旧旁路已经破坏过计数的卡单应取消后重下，不能凭 100% 或库存猜测补推进游标。
